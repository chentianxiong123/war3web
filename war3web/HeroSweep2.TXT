The sweep converged on a small number of ENGINE faults that surface on hero
after hero, rather than on per-hero mistakes. Ranked by what a fix buys:

 1. X13  34 abilities across 20 of 26 heroes -- 11 of them ultimates -- can
         never be levelled past rank 1, because two compiled tables disagree
         about how many levels an ability has and the one that gates skill
         points has no fallback. Already recorded for 3 abilities; now
         measured at 34. Biggest single gameplay defect found.
 2. X1   108 of 108 cleared art fields across 87 abilities come back from
         the base defaults. NOT cosmetic: where the field is the missile,
         the ability gains a projectile and the whole payload is deferred to
         impact, which delays damage and breaks two channelled spells (X3).
         GATED on an unproven premise -- see the entry before touching it.
 3. recalc's isHero gate  Carried burn damage and attribute bonuses reach
         only heroes, so Ace's fire wall and Byakuya's petals -- the damage
         half of two signature ultimates -- deal nothing. Three sightings.
 4. X11  setAbilityLevel(...,0) DELETES an ability here. The map reads a
         level off the wrong variable in at least two places, so the payload
         silently vanishes; in retail it may clamp to 1 instead. ONE SOURCED
         ANSWER settles Uryu's A03F, Kimimaro's A047 and Gaara's A05P.
 5. X10  A numeric stop order force-casts the unit's first ability. Real,
         player-visible, and a new case of a defect already on record.

X4. [VERIFIED, and the retail question is SETTLED] UnitRemoveAbility with a
    BUFF id must strip the buff, and here it does not.
    Blizzard.j:2588-2590 defines the World Editor's own "Remove Buff" action
    as UnitRemoveBuffBJ(buffcode, unit) { return UnitRemoveAbility(unit,
    buffcode) }, and UnitHasBuffBJ (:2583-2585) as GetUnitAbilityLevel(unit,
    buffcode) > 0. So passing a buff code to UnitRemoveAbility IS how
    Warcraft III removes a buff -- not UNESTABLISHABLE after all.
    The port: engine.js:638 -> world.removeAbility world.js:822-828 deletes
    from u.abilities, calls holdReleasedBy and recalc, and never prunes
    u.buffs; u.buffs is pruned only on expiry (world.js:2089), and
    abilityLevel (world.js:829-846) answers UnitHasBuffBJ off u.buffs while
    b.until > now.
    Two corrections to the finder. The map does this in THREE places, not
    two: formatted.j 6149 'Bmlt' (a buff of A04X/A011, Amls), 6484 'B00X',
    7481 'B00H'. And removeAbility is NOT buff-blind -- it already calls
    holdReleasedBy (world.js:1970-1977), built for this very pattern. It does
    nothing for B00X only because the AEer case (abilities.js:653-667)
    returns {ok:true} with no `hold`, where Amls (abilities.js:706-719)
    returns one and castEffect stores it (world.js:1907). The fix is one
    `hold:` return away, not a new mechanism.

X10. [VERIFIED as a mechanism, BUT MY FRAMING WAS WRONG IN FOUR WAYS AND IT
    IS NOT NEW] A numeric stop order force-casts an ability instead.
    world.js order() (~951-958) tests for a numeric order and calls
    castDummy -- "run this unit's first non-passive ability" -- BEFORE it
    ever checks whether the order is a stop. Warcraft III order id 851972 is
    stop, and the map issues IssueImmediateOrderById(GetTriggerUnit(),
    851972) to cancel a cast at 6 sites (grep -c "851972" = 6). So every one
    of those refusals instead makes the hero cast their first non-passive
    ability. For Byakuya that is always A02F (Blink), because A02F is
    granted at unit creation (world.js:447) before any skill point is spent
    and AInv is passive, so it is deterministically first in his ability
    map -- and with no target passed, tx,ty default to his own position, so
    distance 0 is clamped UP to Ebl2 = 50 and he teleports 50 units due east
    with no art. castDummy also returns true without checking the ability
    ran, and bypasses castEffect, so no cooldown or mana is spent.
    The mechanism is confirmed twice over: castDummy returns at
    world.js:957 before the stop test, and even if it did not, String(851972)
    could never match the /stop|halt/ test at :959.
    FOUR CORRECTIONS, all against what I wrote first:
     1. "851972 is stop" is NOT derivable in this repo. There is no order-id
        table in war3_extracted, and OrderId() here is a hash of ours that
        can never match a literal the script passes. TODO.txt:1281-1283
        already says exactly this. The reading is supported only by the six
        call contexts, which all read as "abort".
     2. Only 4 of the 6 sites are cast cancels. Line 3988 is an item-use
        trigger; line 5183 is an attack trigger that stops the ATTACKER, and
        that unit carries a passive-base ability, so castDummy returns false
        and the stop is silently dropped instead of becoming a cast.
     3. "Instead of stopping the hero" is wrong: interruptCast(u) runs
        FIRST, unconditionally (world.js:955), so a cast in progress IS
        broken off. What is lost is the idle order and the cleared path --
        the unit keeps walking or attacking -- plus the spurious hop.
     4. It does NOT break three of Byakuya's gates. Two hold correctly and
        only suffer the hop. A00T's IS broken, by a DIFFERENT cause:
        castEffect runs runAbility before firing SPELL_EFFECT, AUls is not
        in CHANNEL_HOLDS, and the swarm list is one interruptCast never
        touches -- so the petals keep spawning for the full duration and the
        cooldown was already stamped. That persists even if the stop were
        handled correctly.
    AND IT IS NOT NEW: TODO.txt:1275-1283 already records "castDummy runs
    the first ability the dummy holds, not the one ordered" with the Rock
    Lee example, and HeroSweep.half1.json records the same for the blink
    guard. This is a new CASE of a recorded defect, not a discovery.
